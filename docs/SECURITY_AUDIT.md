## 2. Server-Side Payment Verification Design

### 2.1 Cryptographic Verification Flow (`/api/verify-razorpay-payment`)
Rather than granting any payment-confirmation RPC to the browser, payment confirmation is strictly isolated to a server-side Cloudflare Worker endpoint implemented in [Frontend/src/lib/server-payment.ts](file:///c:/Users/Smit%20Gandhi/Desktop/SMIT/DDD/darsh-dental-glow/Frontend/src/lib/server-payment.ts) and routed in [Frontend/src/server.ts](file:///c:/Users/Smit%20Gandhi/Desktop/SMIT/DDD/darsh-dental-glow/Frontend/src/server.ts):

1. **Client Action:** When Razorpay Standard Checkout returns success in the doctor portal, `doctorApi.verifyRazorpayPayment` dispatches a `POST` request to `/api/verify-razorpay-payment` with:
   - `orderId`: Supabase order UUID
   - `razorpayPaymentId`: Payment ID (`pay_...`)
   - `razorpayOrderId`: Razorpay order ID
   - `razorpaySignature`: Hex signature generated by Razorpay
   - `Authorization: Bearer <supabase_jwt>`
2. **Session Authentication:** The server verifies the caller's JWT using `supabase.auth.getUser(token)`. Unauthorized requests are rejected with HTTP 401.
3. **Cryptographic HMAC-SHA256 Check:**
   Using the Web Crypto API, the server computes:
   $$\text{HMAC-SHA256}(\text{key} = \text{RAZORPAY\_KEY\_SECRET}, \text{data} = \text{razorpayOrderId} \parallel "|" \parallel \text{razorpayPaymentId})$$
   and verifies that it matches `razorpaySignature`.
4. **Order Ownership & State Validation:**
   The server queries `public.orders` to confirm:
   - `order.id = orderId`
   - `order.user_id = auth_user_id`
   - `order.order_status != 'cancelled'`
   - `order.payment_status != 'paid'` (idempotent: returns HTTP 200 if already paid)
5. **Database Update:** The order is marked `payment_status = 'paid'`, `payment_id = razorpayPaymentId` via the server client.

## 3. Server-Side Order Creation & Price Validation Design

### 3.1 Eliminating Client-Supplied Prices (`create_doctor_order`)
To ensure buyers cannot purchase products at manipulated prices:
1. The browser passes only `{ product_id, quantity }`.
2. The `create_doctor_order` PostgreSQL RPC locks each product row (`FOR UPDATE`), confirms `status = 'active'`, and checks `stock >= quantity`.
3. The unit price is retrieved directly from the database:
   ```sql
   v_unit_price := case
     when v_prod.discount_price is not null and v_prod.discount_price > 0 then v_prod.discount_price
     else v_prod.selling_price
   end;
   ```
4. `total_price` is calculated strictly within PostgreSQL as `SUM(v_unit_price * quantity)`.
5. Product inventory is decremented atomically inside the same transaction.
6. If any item is missing, invalid, or out of stock, the transaction rolls back completely.

## 4. Revised SQL Migration (`Frontend/harden_orders_and_roles.sql`)

> [!IMPORTANT]
> The revised migration script below (Revision 3):
> - Completely eliminates any client-callable payment confirmation RPC.
> - Enforces `SET search_path = ''` with fully qualified `pg_catalog.*`, `public.*`, and `auth.*` identifiers to guard against schema search-path injection.
> - Pre-aggregates duplicate product entries in cart payloads to ensure single row locks and accurate quantity validation.
> - Capped at 50 distinct items and 1000 units per line item to prevent denial-of-service / memory overflow.
> - Order numbers are generated with collision detection and retry loops.
> - Inventory restoration guards inactive products against accidental reactivation (`CASE WHEN status = 'out_of_stock' THEN 'active' ELSE status END`).
> - Drops all insecure legacy policies on `products` and `orders`.
> - Restricts product and order updates to depot staff (`admin`, `shop_owner`).
> - Constrains customer order inserts strictly to pending status.
> - Includes read-only Preflight Inspection Queries and Post-Migration Verification Queries.

### Test Results (Node 24 test runner):
- ✔ **Authentic Signature Acceptance:** Confirms standard valid HMAC-SHA256 signature matches.
- ✔ **Case-Insensitive Hex Matching:** Confirms uppercase and lowercase hex signatures match reliably.
- ✔ **Forged Signature Rejection:** Rejects tampered, randomized, or fabricated hex signatures.
- ✔ **Replay Attack / Parameter Swapping:** Rejects when attacker substitutes another valid payment ID or order ID into an authentic signature payload.
- ✔ **Secret Key Mismatch:** Rejects when signed with an incorrect secret.
- ✔ **Input Boundary Safety:** Safe handling of empty, null, or undefined strings without unhandled exceptions.
- ✔ **HTTP Verb Enforcement:** Rejects non-POST requests to `/api/verify-razorpay-payment` and `/api/create-razorpay-order` with HTTP 405 Method Not Allowed.
- ✔ **Missing Environment Configuration:** Fails gracefully with HTTP 500 when Supabase service credentials are absent.
- ✔ **Cart Item Validation:** Rejects empty carts, null product IDs, malformed UUIDs, negative/zero/fractional/excessive quantities (> 1000).
- ✔ **Duplicate Product Aggregation:** Consolidates multiple cart entries for the same product and enforces 50-item cap and 1000-unit aggregated cap.
- ✔ **Inventory Status Restoration Rules:** Correctly flips `out_of_stock` back to `active`, but strictly preserves `inactive` (discontinued) products.
- ✔ **Provider Amount & Currency Matching:** Verifies exact amount matching in paise and currency in INR against live Razorpay values.
- ✔ **Failed/Non-Captured Payment Rejection:** Rejects payments marked failed or uncaptured.
- ✔ **Concurrency / Race-Condition Guard:** Prevents confirming payment for orders concurrently marked as cancelled.

## 6. Preflight & Post-Flight Deployment Procedures

### 6.1 Preflight Checklist (Read-Only)
1. Run the Preflight inspection query block in Supabase SQL Editor:
   ```sql
   SELECT schemaname, tablename, policyname, permissive, roles, cmd, qual, with_check
   FROM pg_catalog.pg_policies
   WHERE schemaname = 'public' AND tablename IN ('orders', 'order_items', 'products', 'profiles')
   ORDER BY tablename, policyname;
   ```
2. Verify existing database triggers on `auth.users`:
   ```sql
   SELECT tgname, relname, proname
   FROM pg_catalog.pg_trigger tr
   JOIN pg_catalog.pg_class c ON c.oid = tr.tgrelid
   JOIN pg_catalog.pg_proc p ON p.oid = tr.tgfoid
   WHERE c.relname = 'users';
   ```

### 6.2 Cloudflare Worker Secrets (Required for Live Payments)
Before enabling live payments or deploying:

### 6.3 Post-Flight Verification Checklist
1. Run Post-migration queries in Supabase SQL editor:
   - Verify `confirm_razorpay_payment` returns 0 rows.
   - Verify `create_doctor_order`, `cancel_doctor_order`, and `handle_new_user` have `prosecdef = true` and `proconfig = {search_path=""}`.
   - Verify RLS policies on `orders` and `products` are constrained to staff for UPDATE.

### 6.4 Rollback Procedure
If any unexpected issues arise in staging:
1. Re-apply legacy policies if necessary from `Frontend/supabase_schema.sql`.
2. Stored procedures `create_doctor_order` and `cancel_doctor_order` operate additively and do not alter existing schema columns; they can simply be revoked or dropped with `DROP FUNCTION public.create_doctor_order` and `DROP FUNCTION public.cancel_doctor_order`.
